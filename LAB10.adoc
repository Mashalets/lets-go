== Принципы многозадачности в ОС реального времени (RTOS)

RTOS поддерживает *вытесняющую многозадачность*, при которой несколько задач могут логически выполняться параллельно даже на одном ядре. Каждая задача — это независимый поток исполнения с собственным стеком и функцией, обычно реализованной как бесконечный цикл.

Планировщик RTOS управляет выполнением задач на основе приоритетов. Если готова к запуску задача с более высоким приоритетом, она вытесняет текущую. При этом RTOS сохраняет контекст (регистры, стек и т.д.) прерванной задачи, что обеспечивает детерминированное переключение и минимальное время отклика — ключевое требование для систем реального времени.

Если приоритеты задач совпадают, может использоваться *круговое планирование* (round-robin) с тайм-квантами, обеспечивающее равномерный доступ к CPU. При отсутствии готовых задач исполняется *idle-задача*, которая, например, может переводить процессор в энергосберегающий режим.

Каждая задача изолирована в памяти: у неё собственный стек и локальные переменные. Это упрощает отладку и предотвращает ошибки, связанные с совместным использованием данных.

== Асинхронный обмен данными между задачами

В системах с RTOS задачи часто обмениваются информацией с помощью *почтовых ящиков*. Это механизм передачи сообщений, при котором одна задача отправляет данные, а другая получает их, не мешая исполнению друг друга.

На практике почтовый ящик представляет собой простую очередь сообщений, чаще всего ограниченную одним элементом. Если получатель ещё не забрал предыдущее сообщение, отправка может блокироваться или завершаться неудачей — в зависимости от настроек операционной системы.

Если же получатель обращается к пустому ящику, он может быть временно приостановлен до появления новых данных. Такой подход снижает нагрузку на процессор за счёт отсутствия постоянной проверки состояния канала.

Почтовые ящики особенно полезны для передачи событий или коротких команд между задачами. Они позволяют минимизировать связность компонентов и упростить архитектуру. В более сложных конфигурациях возможна буферизация нескольких сообщений, что повышает гибкость при обработке данных с разной частотой.

Использование почтовых ящиков способствует устойчивости и предсказуемости поведения многозадачной системы, особенно в условиях ограниченных ресурсов.

== Защита общих ресурсов с помощью мьютексов

В многозадачных системах задачи часто обращаются к одним и тем же данным или устройствам — например, к UART-интерфейсу, глобальным переменным или файлам. Чтобы избежать конфликтов при одновременном доступе, применяются *мьютексы* — механизмы взаимного исключения, позволяющие выполнять критические участки кода строго по очереди.

Принцип работы мьютекса прост: задача, прежде чем использовать общий ресурс, должна захватить мьютекс. Если он свободен — доступ разрешён. Если мьютекс уже занят другой задачей, текущая будет ждать его освобождения. После завершения работы мьютекс освобождается, и следующая задача может продолжить.

Это исключает *состояния гонки* — ситуации, при которых несколько задач одновременно изменяют одни и те же данные, вызывая непредсказуемое поведение. Например, без синхронизации одновременный вывод в консоль несколькими задачами может привести к искажённым сообщениям.

Современные RTOS обычно поддерживают *приоритетное наследование*, чтобы избежать так называемой *инверсии приоритетов*. Если низкоприоритетная задача удерживает мьютекс, необходимый более приоритетной задаче, её приоритет временно повышается, чтобы ускорить освобождение ресурса.

Мьютексы делают поведение системы предсказуемым и стабильным даже при большом количестве параллельных задач.

== Абстракции для работы с периферийными устройствами: `ILed` и `IButton`

При разработке программ для микроконтроллеров часто используется подход, который отделяет логику работы системы от низкоуровневых операций с аппаратурой. В этом контексте абстракции, такие как интерфейсы `ILed` и `IButton`, служат для изоляции взаимодействия с периферийными устройствами (светодиодами и кнопками) от конкретных реализаций на уровне регистров.

Этот подход, основанный на объектно-ориентированном программировании, является примером *Hardware Abstraction Layer* (HAL). Он позволяет задачам работать с устройствами через высокоуровневые методы, такие как `led->On()`, `led->Off()` для управления светодиодом или `button->IsPressed()` для проверки состояния кнопки, не беспокоясь о том, как эти операции реализованы на уровне низкоуровневых регистров GPIO.

Главное преимущество заключается в гибкости: код, использующий интерфейсы `ILed` и `IButton`, не зависит от конкретной аппаратной реализации. Это позволяет легко заменять физические устройства (например, использовать эмуляцию кнопки для тестирования), не меняя остальную логику программы. Такой подход реализует принцип *инверсии зависимостей*, что значительно упрощает поддержку и расширение программы.

== Настройка тактирования и GPIO на STM32F411

Для корректной работы системы на *STM32F411* необходимо правильно настроить систему тактирования и порты ввода-вывода (GPIO) в соответствии с документацией.

=== Тактирование через HSI

Микроконтроллер STM32F411 использует внутренний высокоскоростной RC-генератор HSI с частотой 16 МГц. По умолчанию после сброса система использует HSI как источник тактовой частоты (`RCC_CFGR.SW = 00`).

HSI не требует внешнего кварца, однако его точность может быть ограничена из-за разброса параметров и температуры. Поэтому для периферии, требующей высокой точности (например, USB или UART с точным baud-rate), часто используется внешний генератор HSE.

Для учебных проектов HSI вполне подходит. Также возможно использование PLL для увеличения частоты. Выбор источника тактовой частоты регулируется в регистре `RCC_CFGR`, где поле `SW` определяет источник, а состояние отображается в поле `SWS`.

=== Инициализация GPIO

Первым шагом инициализации является включение тактирования нужных портов через регистр `RCC_AHB1ENR`, который управляет тактированием портов AHB1. Например, для активации порта A используется бит `GPIOAEN` (бит 0), а для порта C — бит `GPIOCEN` (бит 2).

После включения тактирования нужно настроить режим работы выводов:

* `GPIOx_MODER` — определяет режим (вход, выход, альтернативная функция, аналоговый).
* `GPIOx_OTYPER` — тип выхода (например, *push-pull* для управления светодиодом).
* `GPIOx_OSPEEDR` — скорость переключения.
* `GPIOx_PUPDR` — включение подтягивающих резисторов (pull-up или pull-down).

Для светодиода вывод настраивается как цифровой выход (`01` в `MODER`), а для кнопки — как вход (`00` в `MODER`). В зависимости от схемы подключения кнопки, может быть использован *pull-up* или *pull-down*.

Управление выводами осуществляется через:

* Запись в `GPIOx_ODR` устанавливает уровень на выходе (1 — высокий, 0 — низкий).
* Для атомарных операций используется `GPIOx_BSRR`.
* Чтение состояния кнопки осуществляется через `GPIOx_IDR`.

Настройку тактирования и GPIO следует выполнять до запуска планировщика RTOS, чтобы задачи уже работали в правильно настроенной среде. Соблюдение этих шагов обеспечит корректную работу аппаратных абстракций `ILed` и `IButton`, а также всей системы на RTOS.

== Особенности работы RTOS и аппаратной абстракции

В системах реального времени (RTOS) используется вытесняющая модель многозадачности, при которой каждому потоку выделяется собственный стек и назначается определённый приоритет. Ядро планирует выполнение задач таким образом, чтобы при появлении готовой к запуску задачи с более высоким приоритетом она немедленно получала управление процессором. Если ни одна из прикладных задач не активна, управление передаётся функции простоя. Контекст задач переключается с предсказуемой задержкой: RTOS сохраняет состояние текущего потока, восстанавливает контекст приоритетной задачи и возобновляет её выполнение, соблюдая жёсткие требования по времени отклика.

Для межзадачного взаимодействия используется механизм почтового ящика, представляющий собой очередь, способную хранить один элемент. Отправляющая задача помещает сообщение в ящик и продолжает выполнение, тогда как задача-получатель ожидает данные либо до получения сообщения, либо до истечения заданного тайм-аута. Если ящик занят, отправитель переходит в состояние ожидания; в случае невозможности передачи может быть возвращён соответствующий код ошибки. Такой подход обеспечивает логическую изоляцию, например, между обработкой ввода с кнопки и управлением индикацией, исключая необходимость в циклическом опросе.

Мьютекс обеспечивает эксклюзивный доступ к разделяемым ресурсам: поток, захвативший мьютекс, выполняет защищённую секцию, пока не освободит блокировку. Остальные задачи при этом приостанавливаются. Внутри RTOS применяется механизм приоритетного наследования: если мьютекс удерживается задачей с низким приоритетом, а более приоритетная задача ожидает доступ, системе разрешено временно повысить приоритет первой, чтобы избежать приоритетной инверсии.

Аппаратные компоненты приложения отделены от логики управления посредством интерфейсов `ILed` и `IButton`. Эти абстракции скрывают детали взаимодействия с GPIO-регистрами: метод `ILed::Switch` отвечает за переключение состояния светодиода, а `IButton::IsPressed` — за считывание состояния входного сигнала. Такой подход упрощает модульное тестирование и переносимость кода между платформами.

Контроллер STM32F411 после сброса запускается от внутреннего генератора HSI с частотой 16 МГц. В регистре `RCC_CFGR` поле `SW` устанавливается в `00`, что соответствует выбору HSI как источника системного тактирования. Перед использованием портов необходимо активировать их тактирование, установив соответствующие биты `GPIOAEN` и `GPIOCEN` в регистре `RCC_AHB1ENR`. Линия `PA5` настраивается в режим выхода для управления светодиодом, в то время как `PC13` остаётся входом и используется для подключения кнопки.

== Реализация задачи обработки кнопки

Класс `ButtonTask` реализуется на основе шаблонного класса `Thread`, что обеспечивает автоматическое выделение стека размером 2 КБ. В конструктор передаются интерфейс управления кнопкой, однозначный почтовый ящик и мьютекс, синхронизирующий доступ к стандартному выводу.

Задача работает в бесконечном цикле: с периодом в 10 мс вызывается метод `IsPressed`, при этом краткая задержка помогает отфильтровать дребезг контактов. При обнаружении нажатия кнопки счётчик увеличивается и отправляется в почтовый ящик. Если очередь занята, поток ожидает освобождения ячейки, но не дольше 100 мс. После отпускания кнопки цикл продолжается, обеспечивая стабильную реакцию на пользовательский ввод.

[source,cpp]
----
class ButtonTask : public OsWrapper::Thread<2048>
{
public:
  ButtonTask(IButton& button,
             OsWrapper::MailBox<int, 1>& mailBox,
             OsWrapper::Mutex& mutex)
    : mButton(button), mMailBox(mailBox), mMutex(mutex) {}
  void Execute() override;
private:
  IButton&                   mButton;
  OsWrapper::MailBox<int, 1>& mMailBox;
  OsWrapper::Mutex&          mMutex;
};
----

== Обработка событий в задаче управления светодиодом

Задача `LedTask` отвечает за реакцию на события, инициированные задачей `ButtonTask`. Основной метод `Execute` периодически вызывает функцию `MailBox::Get`, устанавливая тайм-аут в одну секунду. Если в течение этого времени удаётся получить сообщение, извлечённое значение интерпретируется как счётчик нажатий и выводится в стандартный поток. После этого вызывается метод `mLed.Switch`, который переключает состояние светодиода, подключённого к линии `PA5`, обеспечивая визуальную обратную связь.

В дополнение к этому в консоль выводится строка формата `Led Task:123123123123`, что может использоваться как метка или отладочное сообщение. При необходимости исключения конфликтов при выводе в консоль (например, при одновременном доступе из нескольких потоков) можно раскомментировать вызовы методов `Lock` и `UnLock` для активации защиты с помощью мьютекса.

Такая архитектура обеспечивает асинхронную обработку событий и повышает надёжность многозадачного взаимодействия в системе.

[source,cpp]
----
class LedTask : public OsWrapper::Thread<2048>
{
public:
  LedTask(ILed& led,
          OsWrapper::MailBox<int, 1>& mailBox,
          OsWrapper::Mutex& mutex)
    : mLed(led), mMailBox(mailBox), mMutex(mutex) {}
  void Execute() override;
private:
  ILed&                     mLed;
  OsWrapper::MailBox<int, 1>& mMailBox;
  OsWrapper::Mutex&         mMutex;
};
----

== Ранняя инициализация микроконтроллера

Функция аппаратной инициализации вызывается на раннем этапе старта, ещё до создания глобальных объектов и запуска основной логики приложения. На этом этапе активируется внутренний высокочастотный генератор HSI, который устанавливается в качестве основного источника системного тактирования. Затем включается подача тактовых импульсов на порты GPIOA и GPIOC через регистр `RCC_AHB1ENR`.

После активации тактирования настраиваются режимы работы соответствующих линий ввода-вывода: например, `PA5` переводится в режим выхода для управления светодиодом, а `PC13` остаётся входом — как правило, для подключения пользовательской кнопки. Корректное завершение этой процедуры подтверждается возвратом значения `1`, что сигнализирует о готовности системы к дальнейшему выполнению кода.

[source,cpp]
----
extern "C" int __low_level_init(void)
{
  RCC::CR::HSION::On::Set();
  RCC::CFGR::SW::Hsi::Set();
  RCC::AHB1ENRPack<
      RCC::AHB1ENR::GPIOCEN::Enable,
      RCC::AHB1ENR::GPIOAEN::Enable
  >::Set();
  GPIOA::MODER::MODER5::Output::Set();
  GPIOC::MODERPack<
      GPIOC::MODER::MODER5::Output,
      GPIOC::MODER::MODER8::Output,
      GPIOC::MODER::MODER9::Output,
      GPIOC::MODER::MODER13::Input
  >::Set();
  return 1;
}
----

== Запуск приложения и создание задач

В функции `main` происходит инициализация ключевых компонентов системы. Сначала создаются глобальные экземпляры объектов синхронизации — `MailBox` для передачи сообщений и `Mutex` для защиты критических секций. Далее инициализируются аппаратные абстракции: `Led` и `Button`, привязанные к конкретным линиям GPIO, например, `PA5` и `PC13`.

После этого порождаются два потока: `LedTask` назначается высокий приоритет, чтобы обеспечить максимально быструю визуальную реакцию на события, тогда как `ButtonTask` запускается с обычным приоритетом. Это позволяет корректно сбалансировать загрузку процессора между задачами разного назначения.

Финальным этапом выполнения функции `main` является вызов `Rtos::Start`, передающий управление встроенному планировщику задач. С этого момента выполнение программы осуществляется в соответствии с приоритетами и логикой заданных потоков.

[source,cpp]
----
int main()
{
  using namespace OsWrapper;
  OsWrapper::MailBox<int, 1> buttonMailBox;
  OsWrapper::Mutex           mutexIostream;
  Led<GPIOA, 5>              led1;
  Button<GPIOC, 13>          button;
  LedTask    ledTask(led1, buttonMailBox, mutexIostream);
  ButtonTask buttonTask(button, buttonMailBox, mutexIostream);
  Rtos::CreateThread(ledTask,    "LedTask",    ThreadPriority::highest);
  Rtos::CreateThread(buttonTask, "ButtonTask", ThreadPriority::normal);
  Rtos::Start();
  return 0;
}
----

== Синхронизация доступа с помощью мьютекса

Класс `Mutex` инкапсулирует создание и управление системным примитивом синхронизации, предоставляемым ядром операционной системы. Объект мьютекса инициализируется в конструкторе и автоматически освобождается в деструкторе, что исключает утечки ресурсов и ошибки ручного управления.

Метод `Lock` принимает параметр тайм-аута, позволяя задать максимальное время ожидания захвата ресурса. Это предотвращает ситуацию бесконечной блокировки, если ресурс по каким-либо причинам остаётся недоступным.

На уровне реализации используются функции `wLockMutex` и `wUnLockMutex`, поддерживающие механизм приоритетного наследования. Это гарантирует, что задача с высоким приоритетом не будет надолго заблокирована менее приоритетной задачей, уже захватившей ресурс. Таким образом, достигается устойчивое и предсказуемое поведение многозадачной системы при работе с разделяемыми данными.

[source,cpp]
----
class Mutex
{
public:
  Mutex() : handle(RtosWrapper::wCreateMutex(mutex)) {}
  ~Mutex() { RtosWrapper::wDeleteMutex(handle); }

  bool Lock(tTime timeout = static_cast<tTime>(1000))   /* мс */
  { return RtosWrapper::wLockMutex(handle, timeout); }

  void UnLock() { RtosWrapper::wUnLockMutex(handle); }

private:
  tMutex       mutex;
  tMutexHandle handle;
};
----

== Заключение

Рассмотренная архитектура отражает типовой подход к построению RTOS-приложений на базе микроконтроллеров семейства STM32F4. Начальная инициализация выполняется до запуска планировщика, обеспечивая корректную настройку тактирования и портов ввода-вывода. Поведение системы формируется через набор изолированных задач, каждая из которых отвечает за строго определённую функциональность — от обработки кнопки до управления светодиодом.

Для взаимодействия между задачами применяются средства межпоточной синхронизации — почтовый ящик и мьютекс, позволяющие избежать конфликтов доступа и обеспечить своевременную реакцию на внешние события. Аппаратные зависимости инкапсулированы в интерфейсах `ILed` и `IButton`, что способствует модульности, удобству тестирования и лёгкому переносу кода между различными аппаратными конфигурациями.

Использование приоритетов и механизма приоритетного наследования делает поведение системы устойчивым даже в условиях конкуренции за ресурсы. В совокупности эти решения обеспечивают детерминированное выполнение, надёжность и масштабируемость разрабатываемого программного обеспечения.
